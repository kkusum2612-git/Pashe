# Pashe database guide

This guide covers the PostgreSQL database used by Pashe: how it is configured,
started, checked, connected to, migrated, and kept persistent. The database is
for shared user identity and authentication-related records; feature-specific
tables are not implemented yet.

## Database at a glance

| Setting | Value |
| --- | --- |
| Engine | PostgreSQL 17 |
| Compose service | `postgres` |
| Container name | `pashe-postgres` |
| Default database | `pashe_db` |
| Default database user | `pashe` |
| Host binding | `127.0.0.1:5433` by default (`DB_HOST_PORT`) |
| Container port | `5432` |
| Persistent volume | `pashe_postgres_data` |
| Schema management | Flyway SQL migrations |
| Application ORM schema behavior | Hibernate `ddl-auto: validate` |

Compose reads `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD`, and `DB_HOST_PORT` from
the process environment or a root `.env` file. `.env.example` is a template,
not a secret: copy it to `.env` and set a private local password before
starting Compose. The checked-in `.gitignore` excludes `.env` and allows
`.env.example`.

The default host port is `5433` to avoid colliding with a PostgreSQL service
already listening on host port `5432`. Compose still uses PostgreSQL's standard
port `5432` inside the container. Change `DB_HOST_PORT` only if `5433` is also
in use, and use that same value for the backend's datasource connection.

## Start PostgreSQL

From the repository root in PowerShell:

```powershell
Copy-Item .env.example .env
# Edit .env and replace DB_PASSWORD with a private local value.
docker compose up -d postgres
```

The Compose file preserves the existing `pashe_postgres_data` named volume.
PostgreSQL stores its data there, so stopping or recreating the container does
not remove database contents.

To see container state and logs:

```powershell
docker compose ps
docker compose logs --tail 100 postgres
```

## Live database health check

The Compose health check runs `pg_isready` against the configured database and
user. It starts after a short grace period, then retries every 10 seconds. A
healthy service means the PostgreSQL server is accepting connections. Because
`pg_isready` is a server-readiness probe, it does not verify that the configured
user can authenticate, that the database exists, that Flyway migrations ran,
or that application tables exist.

Check the Compose health state:

```powershell
docker inspect --format='{{.State.Health.Status}}' pashe-postgres
```

Expected output is `healthy`. You can also run the same readiness probe directly
inside the container:

```powershell
docker compose exec postgres sh -c 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Expected output includes `accepting connections`. To check an actual SQL
connection and query the database:

```powershell
docker compose exec postgres sh -c 'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

At the `psql` prompt, try:

```sql
SELECT current_database(), current_user, now();
\dt
SELECT name FROM roles ORDER BY name;
SELECT installed_rank, version, success
FROM flyway_schema_history
ORDER BY installed_rank;
\q
```

An alternative is to connect from a host with `psql` installed. It prompts for
the password instead of putting the secret in the command:

```powershell
psql -h 127.0.0.1 -p 5433 -U pashe -d pashe_db
```

Replace the user and database if `.env` uses non-default values.

### Application health is separate

The backend exposes `GET /api/v1/health`, returning a static response that
confirms the web application answered. It does **not** query PostgreSQL. The
frontend's connection card also checks only this HTTP endpoint. Use the
PostgreSQL `pg_isready` check and the SQL query above to assess database
readiness. There is currently no database-aware application health endpoint.

## Database schema

Flyway applies numbered SQL files from
`backend/src/main/resources/db/migration/` when the backend starts.
`V1__initial_setup.sql` is a placeholder (`SELECT 1`) and must remain
unchanged. Current migrations are:

| Migration | Purpose |
| --- | --- |
| `V2__create_users_and_roles.sql` | User identities, role catalog, and user-role assignments |
| `V3__create_authentication_tokens.sql` | Email verification and password reset token records |
| `V4__seed_default_roles.sql` | The default roles |

Hibernate is configured with `ddl-auto: validate`; it checks mappings against
the schema and does not create or update tables. Flyway owns schema evolution.
Once a migration has been applied, do not edit it; add a new migration with the
next available version instead.

### Tables and relationships

- **`users`** — shared identity. `id` is a UUID primary key generated by
  application code. `email` has a unique index on `lower(email)`, so email
  uniqueness is case-insensitive. Passwords are represented only by
  `password_hash`; email verification and enabled flags have database defaults.
  `created_at` and `updated_at` are timezone-aware timestamps. The database
  initializes both on insert; application code must update `updated_at` when
  changing a user.
- **`roles`** — catalog of authorization role names. `id` is a generated
  identity primary key and `name` is unique. V4 inserts `USER`, `ADMIN`,
  `AMBULANCE_OPERATOR`, and `PHARMACY_STAFF`.
- **`user_roles`** — many-to-many link between users and roles. The composite
  primary key `(user_id, role_id)` prevents duplicate assignments and supports
  multiple roles per user. User deletion cascades to its assignments; role
  deletion is restricted while assignments exist.
- **`email_verification_tokens`** — a UUID-keyed record of a token hash, its
  user, expiry, optional use time, and creation time.
- **`password_reset_tokens`** — same structure for password reset token hashes.

Token tables store hashes, not plaintext tokens. Their `user_id` foreign keys
are indexed and cascade when a user is deleted; token hashes are unique in each
table. No SOS, Care Circle, ambulance, blood donation, Health Passport, or
medicine tables are defined yet.

For the complete column-by-column reference and ER diagram, see
[docs/database-schema.md](docs/database-schema.md).

## Start the backend against the database

Docker Compose reads `.env`, but a locally launched Spring process does not
automatically load that file. Set the same values in the PowerShell session
that runs the backend:

```powershell
$env:DB_NAME = "pashe_db"
$env:DB_USERNAME = "pashe"
$env:DB_PASSWORD = "your-private-local-password"
$env:DB_HOST_PORT = "5433"
Set-Location backend
.\mvnw.cmd spring-boot:run
```

The backend listens on port `8080`. Its datasource URL is
`jdbc:postgresql://localhost:${DB_HOST_PORT:5433}/${DB_NAME:pashe_db}`. Set
`DB_HOST_PORT` to the same host port used by Compose. Flyway runs migrations at
application startup, then JPA validates the schema. A missing database, wrong
credentials, or failed migration prevents application startup.

To query the backend health endpoint from another PowerShell window:

```powershell
Invoke-RestMethod http://localhost:8080/api/v1/health
```

The frontend runs on port `5173` and proxies `/api` requests to
`http://localhost:8080`:

```powershell
Set-Location frontend
npm install
npm run dev
```

## Stop and preserve data

Stop the database container but retain it and its volume:

```powershell
docker compose stop postgres
docker compose start postgres
```

Or remove the container and network while retaining the named volume:

```powershell
docker compose down
docker compose up -d postgres
```

Do not run `docker compose down -v` unless you intend to delete the database
volume and all data in it.

For an existing volume, changing `DB_PASSWORD` in `.env` does not change the
password already stored in PostgreSQL. Keep using the existing database role
password or connect to the database and run the `psql` command `\password pashe`
to change it interactively. Do not delete the volume to fix a credential
mismatch.

## Troubleshooting

- **Compose says `DB_PASSWORD` is required:** create `.env` from
  `.env.example` and set `DB_PASSWORD`, or set it in the shell that runs
  `docker compose`.
- **Container is `starting` or `unhealthy`:** inspect
  `docker compose logs postgres`, then run the `pg_isready` probe above.
- **Connection refused:** verify the container is running and healthy, that
  the configured host port (default `5433`) is available, and that the backend
  uses the same `DB_HOST_PORT`, `DB_NAME`, and `DB_USERNAME` values as Compose.
- **Password authentication fails after changing `.env`:** the volume may have
  been initialized with a different password; see “Stop and preserve data.”
- **Flyway reports a failed migration or checksum mismatch:** inspect the
  migration history and logs. Do not edit an applied migration or delete the
  volume as a workaround; correct the issue with a new migration or an
  intentional database repair procedure.
- **Backend health returns but database seems unavailable:** the current
  `/api/v1/health` endpoint is static and is not a database health check. Probe
  PostgreSQL directly as described above.
